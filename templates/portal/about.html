{% icon 'search' %}What it does

ScoutBox turns a candidate profile, active Resumes, engagement preferences and selected sources into a repeatable discovery pipeline. It searches for niche remote work and relevant companies, validates the underlying pages, and evaluates the evidence against the profile rather than treating every search hit as a lead.

Qualified results are consolidated into Opportunities for actionable roles or Hidden Leads for companies worth researching or approaching. Application material and Prepare Outreach drafts then flow into Applications & Outreach, where ScoutBox keeps company/role context, drafts, documents, status history, mailbox reconciliation and outcomes together.

{% icon 'workflow' %}Main workflow

{% icon 'step1' %}DiscoverFind candidate URLs from preferred sources and custom domains.
{% icon 'step2' %}ValidateConfirm the target page is live and represents a real role or organization.
{% icon 'step3' %}AnalyseEvaluate fit, remote eligibility, freshness and useful signals.
{% icon 'step4' %}ReviewRead and triage Opportunities and Hidden Leads.
{% icon 'step5' %}PrepareCreate application or outreach material from the selected evidence.
{% icon 'step6' %}TrackFollow application status, replies and outcomes.

{% icon 'info' %}Core concepts

Opportunities are actionable roles. Hidden Leads surface relevant companies or needs before a formal role exists. Campaigns steer discovery. Search Sources control where ScoutBox looks and which Local discovery engines find initial URLs. Applications & Outreach keeps prepared drafts, submitted applications, status history, role/company details, documents and mailbox reconciliation in one place.

{% icon 'edit' %}Configuration

Start with Candidate Profile and Engagement Preferences, upload active Resumes in Candidate Profile, configure an AI runtime, then choose Search Sources. For Local AI Discovery, configure local Ollama/hardware and source-provider API keys where available, then review Discovery Markets and Custom Domains. For remote/cloud API discovery, configure OpenAI, Gemini or OpenRouter with an API token and model, then select the Cloud Web routes under AI & Discovery.

{% icon 'review' %}Why use ScoutBox

Generic search is broad and stateless, while a general chat interface does not by itself preserve the full path from discovery through outreach and application tracking. ScoutBox keeps the same profile, preferences and source policy attached to repeated scans, then preserves provenance, validation, fit signals, notes, contacts, generated material, mailbox activity and outcomes so results remain explainable and reusable instead of being reconstructed from scratch.

That continuity makes repeated niche searches practical: weak or stale pages can be filtered out, promising employers can be revisited, and each application can be traced back to the evidence and discovery path that produced it.

It also keeps discovery quality visible over time, so source yield, direct-site checks, AI decisions and application outcomes can be compared without losing the context behind each record.

{% icon 'runtime_cloud' %}Discovery Mode

Local AI Discovery uses local Ollama models plus configured direct sources and search engines. It keeps AI processing on your hardware and avoids cloud-token charges, but needs suitable local hardware and its speed/quality depends on the local model and source coverage.

Cloud Web Discovery uses a configured OpenAI, Gemini or OpenRouter API token and provider-native web research. It reduces local hardware requirements and can provide broader web synthesis, but consumes provider quota/cost and sends research context to that provider. Direct-capable sources may still run directly; ScoutBox search-engine source scraping is bypassed in Cloud Web.

Current config: {% if portal_settings.discovery_mode == 'cloud_web' %}Cloud AI Discovery{% else %}Local AI Discovery{% endif %}. Change this under AI & Discovery.

{% icon 'architecture' %}Overall System Architecture

Django + GunicornServe the ScoutBox UI and API endpoints. User actions persist state in PostgreSQL and queue long-running work instead of blocking the browser.
Celery Beat + Redis + WorkersCelery Beat schedules campaigns and recurring maintenance. Redis carries queued jobs to Celery workers that execute discovery, enrichment, mail and diagnostics.
Discovery and AICloud Web uses configured cloud AI research. Local discovery combines search providers with Ollama on an available macOS or NVIDIA GPU.
Search and page retrievalWorkers call search engines and retrieve candidate pages, then validate evidence before qualification and enrichment.
PostgreSQLStores durable Campaigns, Opportunities, Hidden Leads, Address Book contacts, applications, settings and operational history.
Records and follow-throughQualified evidence becomes durable records that feed Applications & Outreach, status tracking and notification workflows.
SMTP / IMAP and persistent mediaMail integrations deliver digests and support application workflows, while persistent storage holds uploaded and generated files.
Usage and diagnosticsAI requests, provider activity, resource samples and diagnostic data are collected across the web and worker paths for visibility and troubleshooting.

{% icon 'database' %}Database Info

ScoutBox stores durable application state in PostgreSQL through Django. Application tables use the portal_ prefix. The map below is intended for learning and read-only troubleshooting; prefer the ScoutBox UI or Django ORM for edits because direct SQL bypasses validation, audit behavior and application workflows.

Core workflow tables

portal_opportunityOpportunity — discovered roles, fit, status, company context, source URLs and freshness data.
portal_companyleadCompanyLead — Hidden Leads, company research, public contact evidence and fit score.
portal_contactContact — Address Book people and company contacts, including researched company context.
portal_applicationApplication — one-to-one application/outreach record linked to an Opportunity.
portal_campaignCampaign — saved discovery criteria, sources, locations and scheduling inputs.
portal_campaignrunCampaignRun — individual campaign executions, stage, progress, provider/model and outcome.
portal_backgroundjobBackgroundJob — queued/running maintenance, enrichment, import and preparation work.
portal_searchsourceSearchSource — configured discovery/search providers and source settings.
portal_documentassetDocumentAsset — uploaded resumes, cover letters and other reusable source documents.
portal_importcandidateImportCandidate — parsed candidates from text, documents or mailbox imports before final persistence.

Relations, history & diagnostics

portal_opportunity_campaignsOpportunity ↔ Campaign — Django many-to-many bridge connecting an Opportunity to one or more Campaigns.
portal_companylead_campaignsHidden Lead ↔ Campaign — many-to-many bridge preserving Campaign provenance for Hidden Leads.
portal_opportunityevidenceOpportunityEvidence — structured evidence rows attached to an Opportunity.
portal_applicationstatuseventApplicationStatusEvent — status-change history for Applications.
portal_preparedapplicationfilePreparedApplicationFile — generated CV/cover files associated with an Application.
portal_generatedtextversionGeneratedTextVersion — generated email/application text versions with provider/model provenance.
portal_airequestlogAIRequestLog — AI request stage, status, provider/model, duration and token metadata.
portal_chatbotmessageChatbotMessage — Chatbot conversation history, role, session and source provider/model.
portal_usagemetricUsageMetric — provider/stage usage events, token counts, requests, pages and errors.
portal_resourcesampleResourceSample — CPU, RAM, disk and GPU telemetry samples used by Resource Usage.
portal_resourcehourlyResourceHourly — durable hourly CPU, RAM and GPU roll-ups used to preserve long-range Resource Usage history.

{% icon 'terminal' %}Terminal & SQL examples

Run these from the ScoutBox directory. Examples use the active PostgreSQL user/database from the db container. Read queries are safe for learning; backup before any direct write or restore.

Open PostgreSQLStart an interactive psql session against ScoutBox's active database.
docker compose exec db sh -lc 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB"'
Explore the schemaInside psql, list ScoutBox tables and inspect columns, indexes and relationships on a specific table.
\dt portal_*
\d portal_opportunity
\d portal_opportunity_campaigns
Recent OpportunitiesA simple read query for the newest active Opportunity records.
SELECT id, company, title, status, fit_score, country, created_at
FROM portal_opportunity
WHERE user_deleted = false AND suppressed = false
ORDER BY id DESC
LIMIT 20;
Join Opportunities to CampaignsFollow the many-to-many bridge to see which Campaign produced or retained each Opportunity.
SELECT o.id, o.company, o.title, c.id AS campaign_id, c.name AS campaign
FROM portal_opportunity AS o
LEFT JOIN portal_opportunity_campaigns AS oc ON oc.opportunity_id = o.id
LEFT JOIN portal_campaign AS c ON c.id = oc.campaign_id
WHERE o.user_deleted = false
ORDER BY o.id DESC, c.name
LIMIT 50;
Join Hidden Leads to CampaignsUse the Hidden Lead bridge table to verify Campaign provenance.
SELECT l.id, l.company, l.status, l.score, c.id AS campaign_id, c.name AS campaign
FROM portal_companylead AS l
LEFT JOIN portal_companylead_campaigns AS lc ON lc.companylead_id = l.id
LEFT JOIN portal_campaign AS c ON c.id = lc.campaign_id
WHERE l.user_deleted = false
ORDER BY l.id DESC, c.name
LIMIT 50;
Join Applications to OpportunitiesApplications have a one-to-one relation to Opportunities, so the foreign key lives on portal_application.
SELECT a.id AS application_id, a.status AS application_status,
       o.id AS opportunity_id, o.company, o.title, o.status AS opportunity_status
FROM portal_application AS a
JOIN portal_opportunity AS o ON o.id = a.opportunity_id
WHERE a.deleted_at IS NULL
ORDER BY a.id DESC
LIMIT 30;
Campaign execution historyJoin a Campaign to its runs to inspect stage, model and completion state over time.
SELECT c.name, r.id AS run_id, r.status, r.stage,
       r.execution_provider, r.execution_model, r.progress, r.created_at, r.finished_at
FROM portal_campaignrun AS r
JOIN portal_campaign AS c ON c.id = r.campaign_id
ORDER BY r.id DESC
LIMIT 40;
Opportunity evidenceInspect the structured evidence rows supporting an Opportunity without reading raw discovery result payloads.
SELECT o.id, o.company, o.title, e.kind, e.label, e.confidence, e.observed_at
FROM portal_opportunity AS o
JOIN portal_opportunityevidence AS e ON e.opportunity_id = o.id
WHERE o.id = 123
ORDER BY e.observed_at DESC;
AI activity for one OpportunityAIRequestLog uses a soft relation through subject_type/subject_id, so cast the object id to text when joining.
SELECT o.id, o.company, o.title, a.stage, a.status,
       a.provider, a.model, a.duration_ms, a.tokens_in, a.tokens_out, a.at
FROM portal_opportunity AS o
LEFT JOIN portal_airequestlog AS a
  ON a.subject_type = 'opportunity' AND a.subject_id = o.id::text
WHERE o.id = 123
ORDER BY a.at DESC;

{% icon 'redis' %}Redis usage

Redis is ScoutBox's fast in-memory queue and task-result store. Celery Beat and the web process enqueue work; the normal and discovery workers consume it. PostgreSQL remains the durable home for Opportunities, Hidden Leads, Applications and other product records.

What Redis stores hereQueued Celery message envelopes, task-result metadata and short-lived broker state. It is infrastructure state, not the main ScoutBox business database.
Why two queues mattercelery carries general background jobs. discovery is isolated so long campaign discovery runs cannot starve ordinary maintenance and UI-triggered work.
Safe learning rulePrefer INFO, SCAN, TYPE, LLEN, LRANGE, GET and HSCAN. Do not use FLUSHALL, FLUSHDB, broad DEL or queue-pop commands on a live ScoutBox instance.
Check and ping RedisConfirm the container is running, then verify the same Redis server answers requests.
docker compose ps redis
docker compose exec redis redis-cli PING
docker compose logs --tail=100 redis
Understand the current databaseSee server version, memory, clients, persistence and how many keys exist in each logical Redis database.
docker compose exec redis redis-cli INFO server
docker compose exec redis redis-cli INFO clients
docker compose exec redis redis-cli INFO memory
docker compose exec redis redis-cli INFO persistence
docker compose exec redis redis-cli INFO keyspace
Measure ScoutBox queue depthBoth Celery broker queues are Redis lists. Growing counts usually mean workers are stopped, saturated or failing before they can consume work.
docker compose exec redis redis-cli LLEN celery
docker compose exec redis redis-cli LLEN discovery
Sample queued messages without removing themLRANGE reads list entries. Celery envelopes are encoded JSON and may include a base64 body; inspecting them is useful for learning which task/queue headers are present.
docker compose exec redis redis-cli LRANGE celery 0 1
docker compose exec redis redis-cli LRANGE discovery 0 1
Extract basic Celery envelope dataRead the first general-queue message through ScoutBox's configured broker URL and print only useful headers/properties without popping the job.
docker compose exec web \
  python manage.py shell -c "
from django.conf import settings
import json
import redis

r = redis.Redis.from_url(settings.CELERY_BROKER_URL)
raw = r.lindex('celery', 0)
message = json.loads(raw) if raw else {}
print(json.dumps({
    'headers': message.get('headers', {}),
    'properties': message.get('properties', {}),
}, indent=2, default=str))
"
Discover keys safelyUse incremental SCAN instead of KEYS *. Celery result keys commonly begin with celery-task-meta-.
docker compose exec redis sh -lc 'redis-cli --scan | head -n 50'
docker compose exec redis sh -lc "redis-cli --scan --pattern 'celery-task-meta-*' | head -n 20"
Inspect a key before reading itDetermine type, expiry and memory use first. Then use the matching read command: GET for strings, LRANGE for lists, HSCAN for hashes.
docker compose exec redis redis-cli TYPE '<key>'
docker compose exec redis redis-cli TTL '<key>'
docker compose exec redis redis-cli MEMORY USAGE '<key>'
docker compose exec redis redis-cli GET '<string-key>'
docker compose exec redis redis-cli HSCAN '<hash-key>' 0 COUNT 20
Read task-result metadataIf a result key is present, print a bounded sample. Typical Celery result JSON includes task status, result/error metadata and child-task information.
docker compose exec redis sh -lc '
k=$(redis-cli --scan \
  --pattern "celery-task-meta-*" | head -n 1)
[ -n "$k" ] && \
  redis-cli GET "$k" | head -c 4000
'
Check latency and slow commandsUse Redis's own counters when ScoutBox jobs appear delayed. These commands do not modify queue contents.
docker compose exec redis redis-cli INFO stats
docker compose exec redis redis-cli SLOWLOG GET 10
Test through ScoutBox configurationThis avoids assuming a host, port or database number and exercises the exact broker URL Django/Celery use.
docker compose exec web \
  python manage.py shell -c "
from django.conf import settings
import redis

r = redis.Redis.from_url(settings.CELERY_BROKER_URL)
print('PING:', r.ping())
print('Redis:', r.info('server').get('redis_version'))
print('Keys:', r.dbsize())
print('celery:', r.llen('celery'))
print('discovery:', r.llen('discovery'))
"

{% icon 'external_statistics' %}External Statistics

External Statistics is an optional sidecar interface for importing tracking activity from a separate statistics system. ScoutBox sends tracking-link IDs and paths to the service over the internal container network; the service queries its own data source and returns normalized counts and optional event details. If the service is unavailable, ScoutBox continues to operate normally.

Service interfaceProvide GET /health, POST /test and POST /sync. Health reports whether the service is running/configured; test validates its private data source; sync accepts links: [{id, path}] and returns one normalized result per link.
Normalized resultEach result should return id, total, human, first, last and optionally events. Event fields may include source_key, viewed_at, ip_address, user_agent, referrer and raw_uri.
Write your own sidecarThe container may use any database, API or log source internally; ScoutBox does not need its schema. Keep credentials inside the sidecar or its mounted secret, expose only the HTTP interface on the private Docker network, and translate your source data into the normalized fields above.
Connect it to ScoutBoxThe bundled service is reached at http://stats_service:8787. A replacement service can use another internal hostname or port by setting EXTERNAL_STATS_URL for ScoutBox. Enable or test synchronization under Config → External Statistics.
EXTERNAL_STATS_URL=http://stats_service:8787
Minimal sync requestScoutBox posts only generic tracking identifiers and paths. Your service performs the lookup and returns normalized statistics; it does not need access to ScoutBox's PostgreSQL database.
POST /sync
{
  "links": [
    {"id": 42, "path": "/example-tracking-path"}
  ]
}
Minimal sync responseDetailed events are optional. Counts and timestamps are enough for aggregate synchronization; event rows allow ScoutBox to retain per-request history when your source can provide it.
{
  "ok": true,
  "results": [
    {
      "id": 42,
      "total": 12,
      "human": 9,
      "first": "2026-09-01T08:30:00Z",
      "last": "2026-09-20T14:12:00Z",
      "events": []
    }
  ]
}
